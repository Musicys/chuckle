AI 辅助 Java 开发标准规范 (V1.0)

第一章：总则与核心原则
责任归属原则：AI 仅作为辅助工具（定位为"高级代码补全与实习生级生成器"），开发者必须对最终生成的每一行代码、业务逻辑及生产环境安全承担全部责任。
安全红线原则：严禁将 AI 直接用于生产环境的数据修复脚本生成、复杂资金/佣金核算逻辑、核心并发控制逻辑以及复杂多表联查的 SQL 索引优化。
规范优先原则：AI 生成的代码必须无条件服从项目现有的架构规范、编码规范和约束清单，禁止 AI 自由发挥引入非标准依赖或反模式。

第二章：提示词（Prompt）工程规范
约束前置：在发起任何代码生成请求时，必须将项目的"核心约束清单"（如：禁止 SELECT *、参数超 3 个必须封装 Request 对象、强制使用中文注释、所有类和接口必须添加中文 Swagger 注解等）作为最高优先级输入给 AI。
模板化复用：团队需建立并维护统一的"AI 提示词片段库"（如 Manager 层生成模板、手写 XML SQL 模板、代码审查模板），禁止随意编写无结构的提示词，以确保生成代码风格的一致性。
工具适配规范：根据任务复杂度选择合适的 AI 工具。日常 CRUD 与代码补全使用 IDE 插件（如 Copilot）；复杂业务逻辑与项目规范理解使用支持长上下文的工具（如 Cursor + Claude）；国产中间件开发优先使用通义灵码。

第三章：代码生成与执行规范
任务拆解规范：严禁一次性要求 AI 生成包含复杂业务逻辑的完整功能。必须按照"核验（校验逻辑） → 执行（核心业务） → 后置（事务/锁/消息）"三步法进行分步生成与人工 Review。
测试驱动生成（TDD）：对于核心业务接口，必须采用"先测试后实现"的模式。先要求 AI 生成覆盖正常、异常、并发等场景的 JUnit 5 + Mockito 单元测试，人工确认断言逻辑后，再让 AI 生成能通过测试的实现代码。
SQL 与持久层规范：涉及数据库操作的代码，必须明确要求 AI 手写 MyBatis XML，禁止使用 SELECT *，分页查询必须显式指定 limit，条件判断必须使用 <if test="... != null">。
Swagger 注解规范：所有 Controller 类必须添加 @Api(tags = "中文描述")，所有接口方法必须添加 @ApiOperation(value = "中文描述")，所有 DTO/VO 类必须添加 @ApiModel(description = "中文描述")，字段必须添加 @ApiModelProperty(value = "中文描述")。Swagger 注解描述必须使用中文，简明描述接口和字段的业务含义。

第四章：代码审查与质量保障规范
AI 交叉审查：每次代码提交（Commit）前，必须将代码连同项目的"规范-检查清单"输入给 AI，要求其逐条核查并指出不符合项（如事务注解位置错误、Redis Key 硬编码等）。
Swagger 审查：审查时必须逐项检查：Controller 类和方法的 @Api/@ApiOperation 注解是否齐全、描述是否使用中文、DTO/VO 的 @ApiModel/@ApiModelProperty 注解是否齐全且使用中文描述。
人工深度 Review：AI 的审查结果仅作为辅助参考。开发者必须人工验证 AI 指出的问题，并对 AI 生成的分布式锁释放位置、边界条件处理、异常捕获逻辑进行深度复核。
测试兜底机制：AI 生成的代码必须附带单元测试，且核心功能的单元测试覆盖率需达到项目规定的标准，未通过测试的代码严禁合并入主干分支。

第五章：知识沉淀与迭代规范
提示词库维护：开发者在日常使用中，若发现某类提示词生成效果极佳，需及时将其提炼并补充至团队的"AI 提示词片段库"中。
规范动态更新：当项目架构升级或发现 AI 频繁犯某类错误时，需及时更新"约束清单"与"检查清单"，形成 AI 辅助开发的闭环优化。
